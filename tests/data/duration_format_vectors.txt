# Canonical duration formatting vectors (plan 3.2).
#
# ONE contract, read by BOTH implementations' tests: the C++ report writer
# (format_duration) and the frontend (formatDuration). Two hand-maintained copies of
# these cases would drift, and the whole point of the contract is that a duration reads
# identically in the HTML report and in the web UI -- the same run, the same number.
#
# The rule (plan 1.1):
#   * < 10s      at most two decimals
#   * 10s - <60s at most one decimal
#   * >= 60s     rounded to the nearest whole second, "Xm Ys"
#   * zero       "0s"
#   * trailing zeros are always stripped ("19.0s" -> "19s", "1m 0s" -> "1m")
#
# Format: <milliseconds> <TAB> <expected>. Lines starting with # and blank lines are
# comments. A comment must be on its OWN line: the expectation runs to end-of-line, so a
# trailing "# note" would become part of the expected string.
#
# Rounding is HALF-UP on the printed decimal (0.125s -> "0.13s"). Stated explicitly
# because neither language gives it for free: C's "%.2f" rounds half-to-even and
# JavaScript's toFixed follows the binary representation, so both implementations round
# by hand to stay identical.

# --- zero and the sub-millisecond floor -----------------------------------------
0	0s
# A fraction of a millisecond is still time that was measured, so it takes the floor
# rather than reading as "no time at all".
0.4	0.01s
# 0.004s rounds to two decimals as 0s, which would read as "no time at all" for a
# measurement that did take time. The floor keeps the smallest reportable value visible.
4	0.01s
5	0.01s
